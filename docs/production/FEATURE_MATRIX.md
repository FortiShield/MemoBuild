## MB-P0-003 and MB-P0-002 instruction capability matrix

The `v0.2.0` rows in the historical audit above describe the original baseline. The hardening branch has a deliberately limited executable image path. “Compiler validates” refers to syntax, structural, and safety checks; an instruction is production-supported only if it is also applied to stage state or image configuration and covered end to end. The CLI uses a versioned local filesystem snapshot cache for this supported path only; command execution is bypassed because RUN is unsupported.

| Instruction/form | Parser recognizes | Compiler validates | Correct end-to-end semantics executable | Automated coverage | Supported by first production milestone |
|---|---:|---:|---:|---|---:|
| `FROM scratch` with no options or alias | Yes | Yes; must be first and the only stage | Yes; creates a genuinely empty Linux/amd64 stage and OCI rootfs layer | Yes; empty-stage, OCI, and CLI build tests | Yes |
| `FROM <registry-or-local-image>` (tag or digest) | Yes | Yes; rejected with policy reason | No image resolver/unpacker/platform verifier | Yes; tag, local-name, and pinned-digest forms rejected | No |
| `FROM ... AS <alias>` / multiple `FROM` stages | Yes | Yes; rejected with stage/alias diagnostic | No | Yes; alias and second-stage tests | No |
| `WORKDIR` | Yes | Basic one-path syntax | No; no persistent workdir state | Yes; generic recognized-unsupported contract | No |
| `COPY <one context-relative source> <image destination>` | Yes | Exactly one source; rejects flags, wildcard, `--from`, absolute/parent traversal, missing paths, symlinks, and special files; destination normalized within image root | Yes; copies regular files/directories and preserves supported permission bits into the owned stage rootfs | Yes; contents, modes, missing source, traversal, symlink, and no-publication tests | Yes, for the stated form only |
| `RUN <shell-or-JSON-command>` | Yes; raw shell text preserved, JSON form checked | Nonempty and JSON syntax only | No; compiler rejects it before cache access or execution | Yes; rejection-before-execution and sandbox regressions | No |

| `ARG` | Yes | Basic argument identifier | No; build-arg scoping/expansion absent | Compiler rejection covered | No |

The parser handles blank/full-line comments and preserves raw RUN quoting, but RUN is not supported by the build compiler. It rejects physical-line continuations and `# syntax`/`# escape` parser directives. It does not implement Docker variable expansion, shell token semantics beyond the limited supported COPY parsing, or general inline comments. Syntax that is not explicitly handled is rejected or fails validation; it is not coerced into an executable generic node. Symlinks and special files are intentionally unsupported by COPY. The build-level cache key includes versioned normalized operations, source order and contents, metadata, target platform, command metadata, and reproducibility/export settings. The local cache restores a complete validated rootfs tar snapshot and rejects missing/corrupt or unsafe blobs; it has no quota or garbage collector and is not used by the legacy executor or remote cache. It protects against accidental corruption, not an attacker who can rewrite both cache records and blobs.

## Base-image policy for MB-P0-002

The only currently accepted base declaration is exactly one first instruction `FROM scratch`. It is a fixed empty-base identity, not an OCI registry/local image. External OCI refs, mutable tags, digest refs, local image names, aliases, platform flags, and multi-stage builds are rejected. `--pull` does not resolve a base; it fails clearly. No registry request or credential is made. The stage/export path requires a Linux x86_64 host and emits `linux/amd64`.

When external bases are later introduced, the policy is immutable OCI manifest digest only, verified against fetched bytes, with explicit `linux/amd64` platform selection (the current exporter hard-codes Linux/amd64; the isolated backend runs Linux x86_64). The resolver must reject absent/incompatible platform manifests and unavailable images before execution; verified layer extraction must produce the initial stage filesystem. The verified manifest/config/layer identity and selected platform must be part of cache keys/reproducibility inputs. Registry acquisition belongs in a separate trusted resolver and must not expose registry credentials to RUN. No such resolver, unpacker, digest verifier, or authenticated credential provider exists in this checkout.

RUN is unsupported, so no Dockerfile build command executes and no build-time network policy applies to this milestone. The separate MB-P0-001 Bubblewrap sandbox denies network access for the explicit sandbox API. External image acquisition is not supported. Multi-stage references, including `COPY --from`, are outside the first milestone. The OCI layout has automated internal structural/digest validation; OCI runtime loading/execution still requires an external smoke test.
